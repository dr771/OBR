## Context

This is a straight port of SB's already-shipped `wishlist-integration` capability (spec: `../SweatyBetty/openspec/specs/wishlist-integration/spec.md`, design rationale: `../SweatyBetty/openspec/changes/archive/2026-07-13-wishlist-king-integration/design.md`), not new discovery work — see proposal.md and the playbook's reuse ledger. SB already did the live exploration of WK's internals (parse bug, public API shape, `<wishlist-page>` element, lazy-init behavior); those findings are assumed correct here and re-verified live during apply, not re-derived from scratch.

Swish (Wishlist King) is confirmed installed on `original-brands-dev.myshopify.com` (`appInstallations` query, 2026-08-12). Its theme app embeds were off at proposal time (0 `shopify://apps/...` blocks in `config/settings_data.json`) — tracked in MIGRATION-TO-LIVE.md — and were enabled + saved live during this same session (all 5 Swish embeds toggled on in the theme editor, confirmed via a live `settings_data.json` pull and direct `window.WishlistKing` inspection on the published storefront). Code still must not assume the embeds stay on; everything fail-opens to the same state whether WK is absent, embeds get disabled later, or WK just hasn't booted yet.

**Live verification performed this session** (product: FitFlop Slipper Lulu Glitter Toe-Thongs, `/apps/wishlist`, via Chrome DevTools MCP), superseding the "assumed from SB" findings below where they differ:
- `window.WishlistKing.utils.product` prototype confirms `getInputOption`/`getFormOptions` exist — the patch's target methods are real on this install.
- `wk.settings.general.wishlistMode` is `"PRODUCT"` — matches the design assumption.
- `wk._state` prototype confirms `observeWishlist`, `observeProductInfo`, `addWishlistItem`, `removeWishlistItem`, `clearWishlist` all exist as documented.
- **OB's Wishlist Page embed renders option pickers as `<select>` dropdowns, not swatch buttons** (`product_options` is effectively dropdown-mode here, unlike SB's swatch config) — spec scenario wording adjusted accordingly.
- **The Akeneo bracket-key bug did not reproduce live today**, but the underlying condition is real: Admin GraphQL confirms every synced product's raw `option.name` is genuinely bracketed (`[color]`, `[shoe_size_eu]`, `[bottoms_size]`, etc. — checked all 7 products), matching `ob-option-meta`'s documented assumption. However, the storefront's `/products/*.js` and the WK-rendered `<select name="options[color]">` both showed the **stripped, unbracketed** name — the "Translate & Adapt" app (installed on this shop) is translating option *names* for the NL locale, and that translated value is what reaches WK's form-building code today, sidestepping the double-bracket bug SB hit (`options[[color]]`). This is locale/translation-coverage-dependent, not a fix in WK itself — untranslated locales or products would still hit it. The parser patch stays in scope as defense-in-depth, consistent with `akeneo-option-handling`'s existing principle of never trusting a key to be safe just because it looks fine today.
- **Confirmed via live click-through: WK's wishlist-page add-to-cart is a plain `<form action="/cart/add" method="post">` submit** — clicking it causes a full page navigation to `/cart`, not an in-place update. This resolves decision 5 below definitively in favor of the capture-phase AJAX intercept (SB's approach), not the simpler event-subscription-only path.

OB differs from SB in three structural ways that change the port, not just the styling:
1. **Shared option-kind detection already exists** as `snippets/ob-option-meta.liquid` (color/size/generic detection off bracket keys, with `field: 'label'` already returning "Kleur"/"Maat"). SB's label-overlay logic duplicated this inline; OB's must call the existing snippet's logic instead of reimplementing it — meaning the *pattern* (color→Kleur, size→Maat, else humanized) needs to be reachable from client-side JS. Since `ob-option-meta` is Liquid-only, the JS overlay hardcodes the same two label strings directly (matching what the snippet would render) rather than trying to invoke Liquid at runtime — this is not a divergence from the snippet's *behavior*, just where the string lives.
2. **No `custom-theme.js`/`custom.css` monolith.** OB's established convention (`ob-card-swatches.js`, `ob-plp.js`) is one JS file per capability, loaded via an explicit `<script src="{{ '*.js' | asset_url }}">` tag placed where it's needed, and CSS lives in Dawn's existing component files (`component-cart-drawer.css` already took the cart-drawer-line-item-layout CSS, per the playbook ledger's "no custom.css on OB" note). This port follows suit: one `assets/ob-wishlist.js` for all WK-dependent JS (readiness helper, parser patch, label overlay, header badge, PDP heart, cross-sell move-to-cart handling), loaded site-wide from `layout/theme.liquid` since the header heart/badge must work on every page; wishlist-specific CSS added to `component-cart-drawer.css` (drawer/cart cross-sell) and inline `{% style %}` in `sections/header.liquid` (heart sizing) and `snippets/buy-buttons.liquid` (PDP heart), matching how those files already scope their own styles.
3. **OB's cart drawer already has a shipped, bespoke line-item layout** (label-free `Value / Value` variant text, single line-total price, compact X remove icon, borderless asymmetric-gutter panel — `cart-drawer-line-item-layout`). The cross-sell mini-cards must read as part of that drawer, not as an SB-styled insert — new CSS for `.ob-wishlist-cross-sell` is written against OB's actual drawer tokens/spacing, not copied from SB's `.sb-cart-wishlist` rules.

## Goals / Non-Goals

**Goals:**
- Working option selection + human labels on `/apps/wishlist` (swatches kept).
- Header heart + live count badge; PDP heart beside ATC; drawer + `/cart` cross-sell styled to match OB's shipped cart drawer.
- Everything fail-open with WK absent/changed/embeds-disabled; WK's lazy-init untouched.

**Non-Goals:**
- No WK theme-code-editor files (each published file there is an extra chained request; all theme-owned code lives in this repo).
- No changes to collection-card hearts (`wishlist-button-collection` embed) — out of scope, already independently functional per WK's own embed once enabled.
- No variant-level saved state — store runs WK in PRODUCT mode, matching SB.
- Not flipping the WK app embeds on in the shop — that's an admin action tracked in MIGRATION-TO-LIVE.md, not theme code.

## Decisions

1. **Fix the parser at the source (prototype monkey-patch), same as SB.** One patch heals swatches, dropdowns (drawer/cart cross-sell), and buy-all flows at once. Guard: a `__obOptionParseFixed` flag (OB-namespaced, not SB's `__sbOptionParseFixed`); anchored-pattern miss → delegate to original method; any throw inside the patch → delegate to original.
2. **One shared `obWkReady(cb)` helper** (bounded poll ~100ms × 30s) instead of per-consumer polling; consumers: parser patch, header badge, PDP heart, label overlay, drawer cross-sell. The helper only reads `window.WishlistKing` and never touches WK's own lazy-init loader.
3. **Header heart is theme markup with `wk-skip` + its own badge from `observeWishlist`**, same rationale as SB: WK's auto-injected `<wishlist-link>` depends on preset/embed config and dies if that embed is off; a direct subscription is deterministic regardless of embed state. Badge markup mirrors Dawn's `cart-count-bubble` for visual consistency, inserted into the existing `.header__icons` row between the account link and the cart icon (both already present in `sections/header.liquid`).
4. **PDP heart = a button in `.product-form__buttons` + `observeProductInfo`, document-delegated click**, same as SB — no fetch, no MutationObserver guard hack. Subscription callbacks re-query `.ob-wishlist-btn` fresh on each emit so Dawn's `product-info.js` innerHTML swap self-heals; variant id read at click time from the closest form's `input[name="id"]`.
5. **Cart cross-sell reuses WK's `<wishlist-page>` element** with per-instance attributes (`product-options="dropdowns"`, `move-to-cart`), same as SB. **Confirmed live: a capture-phase AJAX intercept is required** — WK's own wishlist-page CTA submits a real `POST /cart/add` form and the browser navigates to `/cart` on click (verified by clicking it live and observing the tab navigate). The intercept captures the form submit inside `.ob-wishlist-cross-sell`, `preventDefault()`s, posts to `/cart/add.js` instead, calls `removeWishlistItem` for move-to-cart, then re-renders the cart drawer sections and opens it — matching SB's pattern. No dependency on a `wishlist:add-to-cart:success` event or an assumed `SB.refreshCartDrawer()`-equivalent; the intercept owns the whole flow itself using Dawn's standard `sectionsToRender`/`fetch` cart update pattern already used elsewhere in this theme (`cart-drawer-line-item-layout`).
6. **`/cart` page gets a new custom section `sections/ob-cart-wishlist.liquid`**, wired into `templates/cart.json` between `cart-items` and `cart-footer` — avoids editing `main-cart-items`. `templates/cart.json` is data, not theme code, so pull the live version first before editing to avoid clobbering any owner customizer changes.
7. **Label overlay is a MutationObserver-driven text rewrite** scoped to WK containers (`wishlist-page`, `.ob-wishlist-cross-sell`), matching `ob-option-meta`'s kind detection: substring match on the bracket key (`color`/`colour`/`kleur` → Kleur, `size`/`maat` → Maat, else humanized key), capitalized standalone, lowercase mid-sentence (CTA interpolation). Locale from `document.documentElement.lang`. Runs on emit + WK re-renders.
8. **Locale keys.** Follow whatever placement pattern `cart-drawer-line-item-layout` already used (check `locales/nl.json`/`en.default.json` for its added keys before adding new ones) rather than assuming SB's `sections.cart.wishlist_*` / `general.wishlist.*` grouping applies unchanged — keep new keys in the same style/nesting as neighboring existing keys in those files.

## Risks / Trade-offs

- **[WK app embeds are off on dev]** → header badge/PDP toggle/cross-sell will visibly show pre-boot/empty state until someone enables them in the theme editor (tracked in MIGRATION-TO-LIVE.md). Mitigation: code correctness doesn't depend on it; verification of the *fail-open* paths can happen now, verification of the *live* paths waits on that admin step.
- **[WK version/behavior on OB's install may differ from what SB observed]** → the parser bug, public API shape, and `<wishlist-page>` attributes are assumed identical (same app, same architecture) but not yet independently re-verified live on OB. Each hook stays name-based and try/fail-open per the spec's "WK internals change shape" scenario, so a mismatch degrades safely instead of throwing.
- **[`<wishlist-page>` inside the drawer adds WK render cost to every page]** → same as SB: element renders empty until WK boots post-LCP; a `:has()` CSS rule hides the whole section when empty; no LCP impact expected since the lazy-init timing is untouched.
- **[`templates/cart.json` is a template file]** → adding the section is data, not Dawn code; a `theme push` of `templates/cart.json` can overwrite owner customizer changes to the cart template. Pull/diff before push, as already noted for this file class in the migration checklist's Theme section.

## Post-verification visual fixes

First-pass CSS shipped three visual bugs, all caught from screenshots after live verification and fixed by going back to SB's proven, shipped solutions rather than re-deriving from scratch:

1. **Header badge rendered as a vertical oval, not a circle.** Cause: the badge was a `<span>`, and Dawn has a global `.header__icon span { height: 100% }` rule (specificity beats `.cart-count-bubble`'s own `height: 1.7rem`), stretching it to the icon's full height while width stayed 1.7rem. SB's badge is a `<div>` — divs aren't targeted by that rule. Switched element + dropped the `hidden`-attribute approach in favor of SB's actual pattern (write text on count > 0, `'99+'` at the cap, clear text at 0; Dawn's native `.cart-count-bubble:empty` rule does the hiding).
2. **PDP heart rendered as a tall thin rectangle, not a square.** Cause: `aspect-ratio: 1` on a flex item whose height comes from `align-items: stretch` doesn't reliably resolve width from height (browser-dependent). SB never relies on aspect-ratio at all — explicit `width: 4.8rem` + `min-height: calc(4.5rem + border*2)`, `flex: 0 0 auto`, `inline-flex`. Also switched from a single evenodd-fill heart path (couldn't produce a true filled look) to SB's two-inline-SVG empty/filled swap.
3. **Cart cross-sell showed raw untranslated option keys (`color: Rust`, `shoe_size_eu: 36`) as plain text, a redundant remove-X, and multiple items packed side-by-side instead of stacked.** WK renders a technical `.wk-label` before each option control that Translate & Adapt doesn't reach (it only strips brackets from the option *name* used in the `<select>`'s own value labels, not this separate label element) — confirmed by comparing against SB's CSS, which explicitly hides `.wk-label`. Also adopted SB's `remove-button { display: none }` (redundant in a move-to-cart flow) and `.wk-grid { display: flex !important; flex-direction: column !important }` (WK's own default lays multiple cards out in columns).

None of these were caught by the earlier live click-through testing because that testing used a single wishlist item and didn't screenshot the header/PDP button at native size — worth remembering for future ports: screenshot small chrome elements (badges, icon buttons) explicitly, don't just confirm the interaction fired.

A follow-up round of user-provided screenshots (with SB's live site as the explicit reference) drove two more cross-sell refinements, both adopted from SB's shipped CSS rather than re-derived: the CTA became an icon-only cart-glyph button (`background-color: currentColor` + SVG data-URI mask, label hidden — works for every locale with no JS icon-swapping) instead of a text-label button, and the size dropdown was narrowed to the minimum useful width while color/pattern dropdowns stop at the width of their longest option. WK renders an absolutely positioned native `<select>` beneath a visible custom text layer, so intrinsic CSS alone follows only the current value; `ob-wishlist.js` therefore measures every color option in the rendered font and writes the stable width through `--ob-wk-option-width`. The width split targets WK's immediate `<wk-option-select>` flex items (with `:has(select[name*="size" i])` covering `shoe_size_eu`, `tops_size`, and `bottoms_size`), while the `.wk-control` and `.wk-content` shells own the shared height and internal padding.

## Migration Plan

Ship code (`assets/ob-wishlist.js`, `component-cart-drawer.css` additions, `sections/header.liquid`, `snippets/buy-buttons.liquid`, `snippets/cart-drawer.liquid`, `snippets/ob-wishlist-cross-sell.liquid`, `sections/ob-cart-wishlist.liquid`, `templates/cart.json`, `layout/theme.liquid`, locale files) → push with `--only <files>` to the main Dawn theme → verify fail-open behavior (WK absent/pre-boot: heart renders, no badge, no console errors) → flag to the user that live end-to-end verification (swatch selection, badge counts, PDP toggle, cross-sell move-to-cart) needs the WK app embeds enabled first, per MIGRATION-TO-LIVE.md. Rollback = revert the theme files; no shop-side state is created by this change (only consumed).
